# P4-SpecTec IL 전체를 Lean 4로 번역하는 계획

## 1. 목표와 흐름

**전체 P4-SpecTec IL의 타입·변수·관계·메타함수·table을 Lean 정의로 직접 옮긴다.** 생성된 정의로 P4의 타입 판단과 실행 결과를 표현하고 성질을 증명한다. 작은 예제부터 구현하되 완료 범위는 전체 명세다. 별도 Lean 실행기와 번역기 전체의 의미 보존 증명은 후속 과제로 둔다.

번역은 **기존 EL → IL elaboration → 선언·의존성 수집 → Lean 타입·관계·표기 생성 → Lean 검사** 순서다. 입력은 [elaboration pass](../../../p4spec/lib/pass/elaborate/elab.ml)의 `Il.spec`이며, IL 식의 타입 주석과 관계의 입력 힌트를 재사용한다. IL 다음 단계인 AL pass의 바인딩 분석·삽입된 조건은 사용하지 않는다. IL 규칙은 선언적이므로 등식 전제는 방향 없이 번역한다. 원본 이름·위치와 생성된 Lean 선언의 대응 정보도 남긴다.

## 2. 공통 구조의 번역

| IL | Lean |
|---|---|
| 기본 타입, 별칭, 레코드, variant | 기본 타입, `abbrev`, `structure`, `inductive` |
| 튜플·optional·목록·타입 매개변수 | 곱 타입·`Option`·`List`·타입 매개변수 |
| 규칙의 변수 | `VarE`의 타입 주석을 쓴 각 규칙의 타입 있는 지역 변수 |
| 관계의 서명과 규칙 | `Prop` 값의 귀납 관계와 전제에서 결론을 도출하는 생성자 |
| 메타함수·table | 결과 인수를 추가한 관계; clause·행을 관계 규칙으로 변환 |
| 데이터 구성식 | 대응하는 Lean 항 |
| 함수 호출과 부분 연산 | 결과 변수와 정의 조건 전제 |
| `IfPr`·`RulePr`·`IfHoldPr`·`IfNotHoldPr` | 등식·조건 명제, 관계 적용, 앞선 관계의 부정 |
| 반복·재귀 | 목록·optional의 원소별 관계, 재귀 호출 전제와 상호 귀납 정의 |

elaboration은 `LetPr`를 만들지 않으며([dimension.ml](../../../p4spec/lib/pass/elaborate/dimension.ml)), 변수 바인딩도 `IfPr (l = r)`로 나타난다. 예를 들어 `$f(A) : B`는 `F : A → B → Prop`가 되고, `g(f(a))`는 중간 변수 `b`를 둔 전제 `F a b`, `G b c`로 연결한다.

관계의 각 규칙과 함수의 각 clause는 결론(clause는 인수와 결과)의 항과 전제를 옮겨 생성자 하나로 번역한다. 인수 순서는 IL `nottyp`의 순서를 유지한다. 입력 힌트는 인수를 바꾸지 않고 `otherwise`의 적용 조건을 정하는 데에만 쓴다. 환경·상태 갱신도 이전 값과 이후 값 사이의 관계로 표현한다.

기준 구조는 [IL AST](../../../p4spec/lib/lang/il/ast.ml)다. variant 포함, `map`·`set` 등은 IL에 정의된 데이터 구조를 유지한다.

## 3. SpecTec 입력의 표기법 재사용

**Prop의 표기는 입력의 `RelD`·`ExternRelD`에 있는 `nottyp`에서 가져온다.** [mixfix 트리](../../../p4spec/lib/domain/mixfix.ml)의 인수 자리·기호·괄호·배치를 그대로 Lean 문법으로 옮긴다.

| 입력 서명 | Lean에서 쓰는 명제 |
|---|---|
| `Type_wf: bound \|- typeIR` | `B \|- typeIR` |
| `Type_alpha: typeIR ~~ typeIR` | `typeIR_a ~~ typeIR_b` |
| `Choose: bool nat nat ~> nat` | `true 1 2 ~> 1` |

일반적인 형태는 `scoped notation`으로 생성하고, 별도 parser가 필요하면 같은 입력 표기를 받는 `syntax`·macro와 출력용 unexpander를 생성한다. 인수 경계와 결합 구조에 맞춰 parser 우선순위를 지정하며, Unicode 치환·관계 이름 태그·추가 쉼표를 도입하지 않는다. 메타함수와 table은 입력의 결과 바인딩 `r = $f<타입 인수>(입력 인수)`를 재사용한다.

표기가 같은 관계는 `P4Judgments.Cast_expl`처럼 관계별 scope로 구분한다. 생성된 규칙은 IL에 기록된 관계 식별자로 연결한다. 정의 뒤에 표기를 선언하며, 상호 재귀 그룹 내부나 여러 동일 표기를 동시에 참조하는 곳에서는 Lean 관계 이름을 사용한다. 원본에 없는 보조 판단과 추가 상태 인수도 이름과 인수를 명시한다.

## 4. 구현과 검증

현재 구현은 `p4spec/lib/lean-skeleton/`의 실행 파일이며 `Pass.elab` 다음에 동작한다. 이후 기존 [공개 진입점](../../../p4spec/lib/p4spectec.ml)의 `elab` 다음에 CLI로 연결한다. 번역 결과와 원본 대응 정보를 반환하고, 오류는 원본 위치가 포함된 `Diagnostic.t`로 반환한다. 파일 쓰기는 CLI에서 수행한다.

| 단계 | 구현 위치와 작업 | 검증 대상 |
|---|---|---|
| 1. 선언·타입 | `translator.ml`: 이름·타입·mixfix 생성자·구조체를 번역 | 기본 타입, 레코드, variant, 타입 인수, 변수 타입 |
| 2. 식·규칙 | `translator.ml`: 결과 변수와 호출 전제를 만들고 규칙·clause·행을 관계로 생성 | 바인딩, 중첩 호출, 관계 간 호출, table |
| 3. 순서·상호 재귀 | `order.ml`: 의존성·SCC·`mutual`·미번역 의존 제거 | 전방 참조, 상호 호출, 순환 속 별칭 |
| 4. 입력 표기 | `printer.ml`: 원본 mixfix와 호출·결과 바인딩을 Lean 문법으로 생성 | 입력 표기로 작성한 증명, 동일 표기의 scope 구분 |
| 5. 반복·선택 | `translator.ml`·`order.ml`: 원소별 반복, `otherwise`, 부정 전제를 생성 | 빈 목록, 길이 불일치, `otherwise`, 부정 호출 |
| 6. 외부 정의 | `builtin.ml`: builtin·extern의 이름·서명에 맞는 정의와 필요한 상태를 연결 | 연결 누락, 정의되지 않는 입력, 상태 변화 |
| 7. 전체 명세 | 전체 IL을 번역하고 남은 미지원 구조를 해소 | 전체 Lean 빌드, 대표 증명, 원본 대응의 누락 |

`Mixfix.args`·`fill`, `Hints.Input.split`·`combine`, `Il.Free`를 재사용한다. 호출 대상과 타입 참조의 의존성은 별도로 수집한다. 상호 재귀 그룹은 같은 Lean 파일에 둔다.

초기 생성물은 `lean/P4Spec/Generated/`의 `Types.lean`, `Semantics.lean`, `source-map.json`이다. 직접 작성하는 기본 연산·외부 모델·증명은 생성 경로 밖에 둔다. `lean/lean-toolchain`에 안정 버전을 고정하고 Lake 프로젝트를 구성한다. 구현할 CLI와 전체 검증 명령은 다음과 같다.

```sh
./p4spectec lean -o lean/P4Spec/Generated spec
lake -d lean build
```

**첫 통합 검증은 `$ite`를 호출하는 `Choose` 관계다.** `p4spec/test/backend-lean/fixtures/choose.watsup`에 표준 라이브러리의 `$ite`와 `Choose: bool nat nat ~> nat`을 정의한다. 규칙의 결과는 `$ite<nat>(b, n_1, n_2)`로 바인딩한다. 파싱·IL elaboration·Lean 생성·증명 검사를 연결해 `true 1 2 ~> 1`, `false 1 2 ~> 2`, `¬ (true 1 2 ~> 2)`를 확인한다.

통합 테스트는 `p4spec/test/backend-lean/`에 두고 새 `@backend-lean` alias로 실행한다. CLI 연결 변경에는 기존 `make build`, `make test-speclang`도 실행한다.

완료하려면 전체 IL의 선언·식·전제가 번역되거나 명시적인 외부 정의와 연결되고, 전체 생성 모듈과 대표 증명이 Lean 검사를 통과해야 한다. 원본 표기와 선언 대응을 확인하며, `sorry`·`admit`이나 임의의 결과를 허용하는 관계로 누락을 메우지 않는다. 외부 가정은 명시한다.

## 5. 보존해야 할 IL 의미

기준은 IL의 선언적 의미다. IL을 직접 실행하는 인터프리터는 없고, AL·SL·PL 인터프리터는 IL에서 파생된 언어를 실행하므로 참고용 교차 확인에만 쓴다. 값과 builtin은 IL `value`와 [builtin 구현](../../../p4spec/lib/interface/builtin/call.ml)을, 수 연산은 [`Num`](../../../p4spec/lib/lang/xl/num.ml)을 따른다.

- **규칙과 clause:** 관계의 규칙과 함수의 clause는 순서 없는 합집합이며, 전제가 모두 성립할 때 적용된다. `otherwise`는 같은 입력(관계는 `hint(input …)`의 자리, 함수는 인수)에 대해 다른 규칙·clause가 유도되지 않을 때만 적용된다. `IfNotHoldPr`는 해당 판단이 유도되지 않음을 요구한다.
- **식의 정의:** 식은 값이 정의될 때만 전제를 만족한다. 함수 호출, 0으로 나누기, 범위 밖 인덱스처럼 정의되지 않을 수 있는 식은 결과 변수와 정의 조건 전제로 번역한다. 연산의 피연산자는 모두 정의되어야 한다.
- **수:** nat − nat과 nat의 부호 반전은 int이고, `/`·`\`는 0으로 나누면 정의되지 않으며, int 나눗셈은 0 쪽으로 버리고 나머지는 피제수의 부호를 따른다.
- **결과 데이터:** optional의 `none`과 P4의 `reject`는 정상적인 결과 데이터일 수 있으며, 규칙의 적용 불가와 구분한다.
- **조건과 반복:** subtype·패턴·인덱스·길이·optional 유무 조건을 유지한다. 반복식과 반복 전제의 목록은 길이가 같고 원소별로 대응하며, optional 반복은 모두 없거나 모두 있다. 반복 변수의 `<-`·`->` 구분은 선언적 의미를 바꾸지 않는다.
- **재귀:** 유한한 도출을 귀납 관계로 표현한다. 함수 인수의 호출도 입력·결과 관계로 연결하고, 생성된 정의가 Lean의 상호 귀납·strict positivity 제약을 만족하는지 검사한다.

## 6. builtin·extern

IL에 본문이 없는 선언(`BuiltinDecD`·`ExternDecD`·`ExternRelD`·`ExternTypD`)과 호출 지점은 자동 번역하고, 의미는 별도의 Lean 정의로 제공한다.

**builtin:** IL 값 위에서 정의된 [기존 구현](../../../p4spec/lib/interface/builtin/call.ml)의 연산·정의역·자료구조 의미를 따른다. `fresh_typeId` 같은 숨은 상태는 이전 상태·결과·이후 상태 관계로 만들고 호출자에도 연결한다. `DebugPr`는 논리적 내용이 없으므로 생략한다.

**extern:** `archState`·`objectState`는 상태 타입으로, 초기화·외부 호출은 입력·결과·상태 관계로 작성한다. 전체 IL 번역 범위와 구체적으로 모델링할 아키텍처의 범위를 구분하고 대상 구현을 명시한다. 외부 구현이 명세를 다시 호출하면 같은 의존성 분석에 포함한다. 추상화한 동작은 명시적인 관계와 가정으로 남긴다.
